# 결정 카드 ② — 심의필번호 자동발번

> 워크스루 완료: 2026-08-08 (역설명 통과). 코드 위치: 광고심의 Service.save() (회사 저장소).

## 배경

번호 형식 `제YYYY-MM-NNNNN호`(월별 순번)를 서버가 자동 채번해야 하는데
백엔드에 미구현 상태였고, 임시로 프론트가 채번하고 있었다(동시성 무방비).

## 방식: "이번 달 최대 번호 조회 → +1"

```
① SELECT 이번 달 최대 번호   → "00002호"
② +1 해서 "00003호"로 INSERT
```

**약점이 내장된 방식이다** — ①과 ② 사이의 틈(race window)에 다른 사용자가
같은 번호를 선점할 수 있다. DB는 INSERT 를 줄 세워줄 뿐,
"낡은 조회로 계산된 번호"를 다시 계산해주지 않는다.

## 결정 1: 유니크 제약이 안전망

```
문제   : 동시 등록 시 같은 번호 2건이 생길 수 있다 (조용한 오염)
장치   : 번호 컬럼의 UNIQUE 제약 → 중복 INSERT 가 DB 에러로 터짐
의미   : "조용한 데이터 오염"을 "시끄러운 에러"로 변환.
        에러는 잡아서 처리할 수 있지만, 오염은 눈치도 못 챈다
```

## 결정 2: 충돌 시 재시도 (최대 3회)

```java
for (int attempt = 0; attempt < 3; attempt++) {
    dto.setNumber(nextNumber());          // 매번 다시 조회해서 +1
    try { return repo.save(dto); }        // 성공하면 끝
    catch (DataIntegrityViolationException e) { /* 선점당함 → 다음 번호로 */ }
}
throw 409 "잠시 후 다시 시도";             // 3연속 충돌 = 비정상
```

두 사용자가 부딪혀도 **둘 다 성공하고 번호가 안 겹친다** —
사용자 눈에는 "DB가 알아서 줄 세워준 것처럼" 보인다. 그걸 앱이 만든 것.

## 결정 3: @Transactional 을 의도적으로 뺐다 ★핵심

```
문제   : 재시도하려면 중복 에러를 catch "루프 안에서" 받아야 한다
함정   : JPA 는 성능을 위해 SQL 을 모았다가 커밋 때 몰아 보낸다(쓰기 지연).
        @Transactional 이 있으면 커밋 = 메서드가 리턴한 "뒤" 에 일어나서
        에러도 그때 터진다 → 메서드 안의 catch 는 시간적으로 앞서 있어 못 잡음
        → 재시도 코드가 통째로 죽은 코드가 된다
선택   : 어노테이션 제거 → repo.save() 가 자체 트랜잭션으로 즉시 커밋
        → 에러가 루프 안에서 터지고 catch 가 잡는다
버린 것 : 시도 간 원자성 — 등록이 INSERT 한 방이라 부분 실패가 없어 무해
```

**역설명 한 줄** (통과 기준): "저장이 커밋 때까지 미뤄져서, 에러도 catch 가 이미
지나간 뒤(메서드 리턴 후)에 터진다. 그래서 뺐다."

## 예상 Q

- "DB 시퀀스 쓰면 되잖아요?" → 맞다, 그게 정석. DDL 변경이라 소유팀 합의가 필요해
  후속 제안으로 분리했고, 시퀀스 도입 시 이 재시도 루프는 통째로 삭제하면 된다.
- "3번 다 충돌하면?" → 409 + "잠시 후 다시 시도" 응답. 3연속 충돌은 부하 이상 신호.
- "롤백은요?" → 단일 INSERT 라 부분 상태가 없다.

## 미해결 (정책)

번호를 직접 지정해 보내면 발번을 우회할 수 있다(프론트 하위 호환용).
프론트가 더는 번호를 보내지 않으므로 차단 가능 — **매니저 결정 대기** (카탈로그 B-06).
